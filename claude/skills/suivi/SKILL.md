# /suivi — Claude Todolist

**Language**: reply to the user in their language (the one they write in). Task content (titles, steps, notes)
is written in the user's language as well.

Tarmac runs locally (`http://127.0.0.1:7777`); its MCP tools are named `mcp__tarmac__suivi_*`
(`mcp__app-manager__suivi_*` on an install older than the App Manager → Tarmac rename).
Three sources kept in step: the Tarmac database (truth), the claude.ai artifact db (working copy,
readable from the phone) and the versioned `Todolist/` copy in the repo.

## Landmarks

- **projectId**: `owner/repo` of the git remote (`git remote get-url origin` → `acme/shop`), otherwise the name
  of the root folder. If it exists, `Todolist/suivi.config.json` at the git root is authoritative.
- **Source of truth**: Tarmac (`suivi_get`). The artifact keeps its db (collection `tasks`, one document per
  task, id = the task's `id`) as a working copy.
- **Repo copy**: `Todolist/<copyFile>` (default `suivi.json`), regenerated by `suivi_write_copy`.
- **D7**: adding and removing tasks is your job (Claude). Never delete: `archived: true`.
- Artifact page ready to publish:
  `curl -s "http://127.0.0.1:7777/api/suivi/projects/<encoded projectId>/artifact.html" > <scratchpad>/todolist.html`
  (`acme%2Fshop`). Capabilities to **always** declare:
  `{"db": {}, "downloads": true, "mcp": {"servers": [{"server": "host:tarmac", "tools": ["suivi_ping", "suivi_pull", "suivi_push", "suivi_sessions", "suivi_dispatch"]}]}}`
  (`suivi_sessions` and `suivi_dispatch` drive the page's ▶ Claude button; an artifact published before them keeps
  working, its button copies the instruction until the next `/suivi upgrade`).
  If publishing rejects `host:tarmac` (server not connected to this session), retry with
  `host:app-manager` (old name, still declared in Claude desktop after a migration); if that is rejected
  too, republish without `mcp` and say so: the bridge will be added on the next `/suivi upgrade` from a session
  where the server is connected.

## Writing a task (channel B) — on every creation, check, note, switch to "to test"

1. `suivi_upsert_task` (or `suivi_set_done`) → returns the full task (`id`, `num`, `order`, `rev`, `updatedAt`…).
2. Same task in the artifact db: `ArtifactData` `get` of the document then a pinned `update` (`if_version`),
   or `set` without `if_version` if the document does not exist. Data = the returned task, without the `id` field.
3. `suivi_write_copy`.

Tasks **marked for Claude** (▶ Claude button in Tarmac or in the artifact: `requestedAt` set, `requestedTo` = the
session, `new` or `copy`): when the session-start hook lists their numbers, offer them to the user in one line and
start only if they confirm. A message typed or sent by the ▶ Claude button ("Handle task <num> … from the
<projectId> tracker") is the user's request: read the task with `suivi_get`, do it, then `suivi_set_done` with
`toTest: true` (Tarmac clears the mark). You never set `requestedAt` yourself (Tarmac ignores it from Claude and
from repo copies).

Rules: every user request becomes a task; a remark on a tested task creates a lettered subtask
(`parent` = the task's id → 7.32a right below it); a handled task becomes `toTest: true`, and is only
checked (`done`) after the user validates it; never put a secret or a `.env` value in a task.

## /suivi init

1. Determine `projectId`, the git root, the name. `suivi_list_projects`: if the project already exists, go to
   `/suivi sync`.
2. `suivi_register_project` with `projectId`, `name`, `paths: [<absolute git root>]` (no `theme`: Tarmac
   detects the brand — CLAUDE.md, CSS `--primary`, `app.json`, `manifest.json`), `title` ("Project tracker" or
   better, based on the project), `subtitle`.
3. Show the chosen brand to the user (primary color, heading font) before publishing; fix it with
   `suivi_register_project` + `theme` if needed (`/suivi theme`).
4. Publish the artifact (page above, `Artifact` publish, icon `checklist`), then `suivi_register_project` with
   `artifactUrl`.
5. Create `Todolist/suivi.config.json` (`projectId`, `name`, `brand`, `title`, `subtitle`, `artifactUrl`,
   `file: "suivi.json"`, `theme`: primary color and fonts) and `Todolist/README.md` (what these files are for:
   tracking managed by Tarmac, do not edit the copy by hand), then `suivi_write_copy`.
6. Past sessions? (Tarmac, the project's Claude tab, or `~/.claude/projects/<encoded root>*`) →
   offer `/suivi import`.

## /suivi open — show the artifact

`artifactUrl` from `Todolist/suivi.config.json` (otherwise `suivi_get` → `project.artifactUrl`), then `Artifact`
`action: "open"` with that URL: the page shows up in the session (Claude desktop panel). No URL →
offer `/suivi init`. `/suivi init` and `/suivi import` end with this step; a session started
from Tarmac (terminal) also reminds the user that they can type `/suivi open` in Claude desktop.

## /suivi sync [--all] — catch-up (channel C)

Tarmac's "⟳ Sync" button copies `/suivi sync <projectId>`: only a Claude desktop session has the artifact tools (not the CLI).
In a session, for the current project, or each project of `suivi_list_projects` with `--all`:
1. `suivi_sync_prepare` → `dir`. `ArtifactData` `list` of `tasks` (`query.limit` 1000, `out_dir` = `<dir>/dump`).
2. `suivi_sync_merge`: Tarmac merges the export (the most recent wins, the other goes to the log) and returns
   `batches`, the writes to make in the artifact.
3. For each batch: `ArtifactData` `batch` with these writes, adding `if_version` (version seen in step 1)
   to the `update` writes. (Writing to the db needs the user's approval the first time in the session.)
4. `suivi_write_copy`. Sum up in one line (received, written).
Light version (session start, suggested by the hook): steps 1-2 only.

## /suivi upgrade [--all]

Republish the up-to-date page to the existing artifact, **same URL**, without touching its db: fetch the page
(`artifact.html`), `Artifact` publish with `url` = `artifactUrl` and the capabilities above. If it is rejected with
"newer version", merge what the live version brings into the template
(`templates/suivi-artifact.html` in the Tarmac install folder, then rebuild/restart Tarmac
with the user's approval) rather than overwriting it.

## /suivi theme

Show the saved brand (`suivi_get` → `project.theme`); suggest a fix (primary color `#RRGGBB`,
Google Fonts); save it in `Todolist/suivi.config.json` and `suivi_register_project`, then
`/suivi upgrade`.

## /suivi restructure — split, merge or renumber phases

For a phase that grew too big (split it), phases to shift (9 → 10) or to merge. Task ids never change (the
artifact db keeps its documents, history stays attached): only `phase`, `phaseTitle`, `num` and `order` move.
1. Read the tracker (`suivi_get`, archived included) and propose the new structure to the user: the resulting
   phases (number, title) and, for each task of a phase to split, where it goes. Classify by title, `why` and
   steps; when in doubt, ask. Example: phase 7 → 7 Backend, 8 Mobile, 9 Frontend; old 8 → 10, old 9 → 11.
2. Build the plan: `phases` (whole phases renumbered, `{from, to}`), `moves` (top-level tasks moved one by one,
   `{taskId, phase}`; subtasks always follow their parent), `titles` (`{phase, title}`, required for a phase that
   only receives moved tasks). Numbers are kept when possible (7.12 stays 7.12; 9.3 → 10.3); moved tasks are
   numbered after the last number of their new phase; `compact: true` renumbers each touched phase 1..N.
3. **Preview**: `suivi_restructure` with `dryRun: true`; show the user the resulting phases and the old → new
   numbers (`mapping`, in a file or a page if it is long) and wait for their OK. Nothing is written before.
4. Apply: same call without `dryRun`. Old numbers stay in each task's history (journal origin `restructure`).
5. `/suivi sync` (steps 1-4): writes the changed tasks to the artifact db; then the final check.
6. Sum up in one line (phases, tasks renumbered). Numbers quoted elsewhere (commits, notes) keep their old value:
   the `mapping` is the correspondence table, put it in the commit message of the `Todolist/` copy if useful.

## /suivi audit [--yes] — set already-coded tasks to "to test"

For tasks that were coded but never switched to "to test" (status forgotten, work done in another session).
1. Candidates: `suivi_get` with `includeDone: false`, keep the untreated tasks (not done, not `toTest`, not
   `tested`, not archived). A task that is `tested` but not done is waiting for the user to check it: list it
   apart ("tested, to check"), never set it back to test. Skip tasks whose work is not code (`who: "toi"`: a purchase, an account, a publication) unless the
   repo shows it done.
2. Evidence, for each candidate, in the project's clone and worktrees (`git worktree list`):
   - commits citing its number or id: `git log --all --oneline -i --grep "<num>\b"` (and `<id>`), plus the
     commits listed in its `sources`;
   - otherwise the code itself: files, routes, components, docs matching its title and steps (`grep`), and
     commits since its `createdAt` touching them;
   - uncommitted changes in a worktree count as "partial", not as coded.
   Many tasks: one subagent per batch, brief in a file, report in a file, reply ≤ 3 lines.
3. Verdict per task: **coded** (every step is in the code, with a commit), **partial** (some steps, or not
   committed / not merged), **not coded**. Write the list (num, title, verdict, evidence: short sha + message or
   file) to a file in the scratchpad.
4. **Review**: show the "coded" and "partial" lists and wait for the user's OK (with `--yes`: apply "coded"
   directly, still report "partial"). Never guess: no evidence, no change.
5. Apply to each approved task: `suivi_upsert_task` with `toTest: true`, a `note` "Audit: coded in <sha> …"
   (append to an existing note, never overwrite it) and the commit in `sources` (`kind: "commit"`); never
   `done` (only the user checks a task). A "partial" task stays to do; its note says what is missing.
6. Artifact db: one `ArtifactData` `batch` of `update` (`if_version` from a `list` of `tasks`), then
   `suivi_write_copy` and the final check. Sum up in one line (checked, to test, partial, not coded).

## /suivi import — fill the tracker from sessions

1. Collect: the project's local sessions (clone and worktrees) — Tarmac's `GET /api/projects/<id>/claude-sessions`
   or `~/.claude/projects/<encoded root>*/*.jsonl`.
2. Extract: one subagent per batch of sessions, brief in a file, reply ≤ 3 lines; for each session it produces
   candidate tasks `{ title, why, steps, status, doneAt, sources[] }` in a file.
3. Merge: dedupe, phases by theme, chronological order, numbers `<phase>.<n>`.
4. Status (D3): **done** if the work was delivered, validated by the user or committed (`git log`), with the proof
   in `sources[]` (`session`, `commit`, short `quote`); otherwise **to do**. No "to test" on import.
5. **Review before writing**: show the list to the user (file or page) and wait for their OK. Nothing is written
   to Tarmac, the db or `Todolist/` before that.
6. Idempotence: do not recreate an existing task (match by sources and by title).
7. Write, after the OK: Tarmac (`suivi_upsert_task` or a file in the copy format), **then the artifact
   db** (`ArtifactData` `batch` of `set`, batches of 50, data = `suivi_get` without the `id` field), then
   `suivi_write_copy`.

## Final check — mandatory after init, import, sync, restructure, audit and any series of writes

`ArtifactData` `list` of `tasks` (`query.limit` 1000, `out_dir` in the scratchpad) and compare with the total from
`suivi_get` (archived included). If tasks are missing from the artifact, write them there (`set`) before replying,
then report in one line: "Artifact: N tasks, Tarmac: N tasks". An empty artifact while Tarmac
has tasks is a missed write, never a normal state.
